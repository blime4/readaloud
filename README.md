# ReadAloud · 朗读工作台

把任意文字读给你听 —— 语音合成用微软 Edge 神经语音，总结与润色用**你这台电脑上的 Ollama 模型**。
文字不出本机，AI 也在本机跑。

工作台页面可以放在 GitHub Pages 上，用任何设备打开都行；但它连的永远是**你本地那台机器**的引擎。

## 长相：pi 风格皮肤（1.9.0）

整套 UI 按 [pi.dev](https://pi.dev) 的设计语言重做，电脑端和手机端同一套：

- **深海军蓝底 + 蓝图网格**：`#0d1116` 底、22px 细线 + 110px 主网格（浅色模式是羊皮纸色）；
- **全直角**：没有一枚圆角，卡片、按钮、输入框、进度条都靠 1px 发丝线分区；
- **衬线标题 + 等宽标签**：标题和逐句稿用衬线体（像书），按钮 / 标签 / 数字统一等宽体
  小写字号 + 大字距；面板上不再有 emoji 图标，全部纯文字；
- **一个强调色**：`#6a9fcc` 蓝，书脊、进度、聚焦框、播放条顶部的渐隐细线都是它；
  书脊配色换成 pi 的土色系（赤陶 / 鼠尾草 / 日光 / 潮蓝），只出现在 3px 竖线和 10% 底纹上；
- 图标重画成同款记号（方框套方芯），PWA 清单和状态栏颜色同步成深底。

主题切换按钮还在右上角：深色是默认，浅色是 pi 的羊皮纸配色。

## 三种用法

| 场景 | 怎么用 |
| --- | --- |
| 网页 | 把链接粘进「读网页」输入框 → 自动抓正文开读。也可以直接把链接粘进文稿框再点朗读 |
| 本地文件 | 点「导入本地文件」，选 TXT / EPUB / MOBI / PDF → 解析出正文后按原文开读，并自动进书架 |
| 手机 | 点「允许手机访问」→ 重启引擎 → 手机浏览器打开面板上给出的地址，书架和进度是同一份 |
| Obsidian | 插件 `readaloud-bridge`：选中文字 `Ctrl+Alt+P` 朗读，`Ctrl+Alt+O` 读整篇，`Ctrl+Alt+S` 总结后朗读 |
| 任意软件 | `Ctrl+Alt+R` 读剪贴板（**内容是链接就自动抓网页正文**）、`+E` 读当前选中的文字、`+S` 总结后读、`+W` 润色后读、`+X` 开工作台、`+Q` 停止 |

## 手机上听（书架）

- **书架**：导入的书自动留在本机（`books/<id>/`，正文 + 进度），换设备不丢。
  点一本书 → 从上次那句接着读；读过的位置实时写回书本身，手机和电脑看到的是同一份。
  1.8.0 起是卡片式：渐变书封（按书名生成）、进度条 + 百分比、状态徽标、
  书名搜索、桌面端还能把文件直接拖进来。`?shelf=1` 直达书架。
- **导入的文件**（1.8.0 修）：手机上一直"点了没反应"的三个原因都修掉了 ——
  ① `accept` 里的 `.epub/.mobi` 在 iOS 没有 UTI，文件会整片变灰，移动端改成
  不设过滤、选完再校验；② `display:none` 的文件框在部分 iOS 上点不动，改成
  移到屏幕外；③ 几十兆的文件上传没进度，看起来像没反应，现在有百分比和取消。
  单文件上限 80 MB，超了会直接告诉你多大。
- **升级与重启**（1.8.0）：设置里「本机引擎信息」有「检查更新 / 升级并重启」，
  点一下就是 `git pull` + 热重启（进程号不变，几秒回来）。顶栏出现
  「⬆ 可升级」时点它也行。引擎自己每 10 分钟查一次，**没人听书时**会自动升级
  并重启；正在播放就等着，不会掐掉。
  「重启引擎」也不再依赖 `readaloud://` 协议，走 `/api/restart`，没装协议也能用。
  拉代码时 **HTTPS 不通会自动改走 SSH**（`git@github.com:...`），并记住通的那条
  —— 否则在 github.com 被代理掐断的网络里，"静默升级"会一直以为没有新版本。
  热重启的过程记在 `restart.log` 里，升级没生效先看它。
- **兼容端口**：老书签 `http://127.0.0.1:8756` 现在指向同一个引擎
  （`config.json` 的 `extra_ports`），不会再打开一份几周前的旧副本。
- **手机访问**：面板「本机引擎信息」里点「允许手机访问」（写入 `host: "0.0.0.0"`），
  重启引擎后用手机浏览器打开给出的地址，例如
  `http://192.168.x.x:8759/?k=9a8bd038`。网址里的 `k=` 是**访问码** ——
  开了局域网之后，同一个 WiFi 里没有这个码的人用不了你的书和登录态。
  手机上"添加到主屏幕"就是全屏应用（带 manifest 和图标）。
- 手机端布局是重新做过的：单屏 + 底部分段（书架 / 文稿 / 逐句 / 设置），
  大按钮、安全区适配，播放条固定在底部。
- **锁屏控制**（MediaSession）：锁屏通知栏显示书名和当前句，耳机线控 /
  蓝牙耳机可以直接播放 / 暂停 / 上一句 / 下一句。
- **屏幕常亮**（Wake Lock）：播放时屏幕不熄灭，边看逐句高亮边听；
  切到后台浏览器自动放锁，纯听不费这块电。
- **回前台自动续播**：iOS 把后台页挂起会顺手暂停音频，回到前台自动接上，
  不用再点一次播放。
- 打开 15 句以上的稿子自动开**后台预合成**（见语音引擎一节），
  本地大模型引擎下听到的每句都是秒出。

## 语音引擎：默认微软神经语音，可切本机大模型

- **edge（默认）**：微软 Edge 神经语音，免费、快、可缓存，几十个中文音色，
  长文逐句朗读唯一跟得上翻页的选择。
- **local（本机大模型 TTS）**：填一个 **OpenAI 兼容**的 `/v1/audio/speech`
  服务地址（CosyVoice2 / Kokoro / GPT-SoVITS / IndexTTS 都提供），
  点「探测」自动列出模型和音色，试听满意再切过去。文字一样不出本机。
  注意 **Ollama 本身不产出音频**（只有文字/视觉/向量），所以"用 Ollama 做 TTS"
  走不通 —— 但同一台机器上跑一个本地 TTS 服务是同样的思路，这里就是为它留的口子。
  本机地址永远直连，系统代理（Clash 之类）不会掺和进来。

### 后台预合成全文（1.7.0，1.10.0 重做）

本地大模型合成一句大约要 1.1 倍于它自己的时长（RTF 0.9～1.3，看显卡状态），
也就是说**「边听边备」在物理上不成立** —— 想听就得独占 GPU。所以预合成的定位是
「不播的时候替你往后备」：

- **一开播就让路**：前端把「正在播」告诉引擎（`POST /api/presynth/hold`），
  预合成做完手上那一句就停，一句都不抢。以前只让 5 秒，而一句长句要听 12 秒 ——
  每句之间它都能插进来干 7 秒活，前台请求排在后面等，长文自然一句一卡。
- **暂停即续备**：暂停/停止时把播放位置传过去，队列直接挪到身后（`at`），
  已经听过的部分不再重备，省下的 GPU 全用在马上要听的那几句上。
- 顶栏会出现「预合成 N/M」进度 chip，点一下即停；暂停时显示「已暂停」。
- 音色/语速/引擎一变，缓存键就变了 —— 前端自动用新参数重开。
- 缓存上限跟着书的长走（`cache_limit` 1200 条 + `cache_mb` 900MB 双上限），
  整本书不会边合成边把自己挤掉 —— 以前 400 条的上限，预合成刚做完，
  最早合成、也最该听的开头那几十句就被自己删了。
- 接口：`POST /api/presynth`（启动，可带 `from`）、`GET /api/presynth`（进度）、
  `POST /api/presynth/hold`（让路/续备）、`POST /api/presynth/cancel`（停止）。

### 播放流水线：单飞有序预取（1.10.0）

本地大模型合成一句话，时间几乎全花在模型上：**8 秒音频要算 8.3 秒**（RTF 1.06），
请求本身的固定开销只有 0.3 秒左右。而且单条请求时 GPU 利用率只有三成多 ——
自回归逐 token 出音频，大半时间在等 CPU 取样和 kernel 启动。所以真正要抓的是
「谁先做」「多出来的那一步转码」和「能不能让 GPU 同时有两条活」：

- 前端一条**有序预取队列**：按播放顺序取，播放也按顺序；但本机允许两条同时在路上。
  实测两条并飞后总吞吐从 **1.0 倍实时升到 1.2～1.3 倍实时**（再多加不涨），
  刚好够把缓冲一点点攒厚。系统语音没这个必要，仍然一条。
- 取回来的音频存成 **Blob URL**，播放时 `src` 指向内存，切换零等待。
  以前每次换句都要重新走一遍网络 + 解码，句间凭空多出 0.2～0.5 秒。
- **起播先备两句**（系统语音不等）：本地大模型没有缓冲就会一句一卡。
  本机大模型还会多备到 9 句（约一分半），因为它的合成速度只在 1.1 倍实时上下，
  听久了会慢慢落后，蓄得深一点才不会每句都停下来等。
- **不要 MP3**（1.10.1 起默认 `tts_local_format: wav`）：本机服务转 MP3 要起一个
  ffmpeg 进程，每句多花 1.0 秒（短句，纯进程启动）到 1.8 秒（长句，还要编码）。
  同一句 8 秒音频：WAV 8.3 秒 vs MP3 10.2 秒 —— RTF 从 1.06 涨到 1.23，
  本来刚好跟得上，一转码就跟不上了。WAV 体积大 5 倍，但走的是本机回环、
  又落在缓存里，不值一提。
- **长句自动切两段并发合成**（1.10.3）：CosyVoice 对长句的流式分块推理效率很差，
  43 字句 RTF 就到 2.5、58 字句 2.05 —— 一句 50 字的要从法语音源讲词源的长句，
  播到那里要干等 25 秒以上。现在超过 `tts_local_split`（默认 30 字）的句子会在
  句内标点处切成两段、两路并发合成、再拼成一条音频返回（WAV 拼 data 块，
  MP3 接帧）。段尾统一收成句号，拼缝处正好是原句该有的停顿；两段各自落缓存，
  倒回去重听时秒拼。实测 58 字句从等 25 秒（RTF 2.05）降到 8～17 秒（1.1 上下）。
- **起播先把显卡叫醒**（1.10.3）：电源请求只能防"继续睡"，救不了已经睡下去的
  频率 —— 躺着听书歇了一会儿再点播放，显卡还在 210MHz，第一句照样慢一倍。
  现在播放开始时引擎会让 TTS 服务跑 2.5 秒的大矩阵乘（`POST /warmup` 的
  gpu_burst），实测把频率从 210MHz 顶到 2745MHz，之后由合成负载接手维持。
- 只保留播放位置前后几段，手机上不吃内存；换书/换音色自动作废重来。
- 等音频时状态栏显示「正在合成第 N 句 · 12 秒」，不再是对着静音干等。

### 测速与提速（1.10.0）

「语音引擎 → 连接设置 → 测速度」会真合成一句，报出 **RTF**（合成 1 秒语音要几秒）：

| RTF | 含义 |
| --- | --- |
| < 0.8 | 很快，边听边备都行 |
| ≤ 1.0 | 跟得上播放 |
| < 1.4 | 偏慢，起播要等两句，之后基本不断（把语速调到 +10% 就跟得上了） |
| ≥ 1.4 | 跟不上，会越听越慢；建议先让它备一会儿，或切回微软语音 |

同一台机器 RTF 能在 0.9～2.6 之间浮动，主要看四件事：

### CUDA Graph 解码（1.11.0，这一次提速 5 倍）

之前所有优化都做完了，RTF 仍卡在 1.5～2.5。分阶段剖析（`_profile_tts.py`）显示
**92% 的时间在 LLM 逐 token 解码**（flow+hift 只占 15%，`empty_cache` 为 0），
每步 47～85ms —— 而 0.5B 模型一步的算力只要几毫秒。继续查：

| 测什么 | 结果 | 说明 |
| --- | --- | --- |
| fp16 matmul 4096³ | 43.6 TFLOPS | 显卡满血，驱动/显存都正常 |
| 小算子（896×896）提交 | 0.088 ms/次 | **Windows WDDM 每个算子都要"递"一次，开销 ~0.1ms** |
| 单步解码 = 24 层 × 10 来个算子 | = 每步两三百次提交 | 纯等待，GPU 利用率只有一两成 |
| GPU 频率/功耗 | 1800～2600MHz / 31W | 频率没问题，就是没活干 |

对策就是 vLLM 在 Linux 上用的那套 —— **CUDA Graph**。做法：
`StaticCache` 把 KV 缓存形状固定（900 位），把「单步解码」整个捕获成一张图，
之后每步只做 `fill_(位置)` + `graph.replay()`，几百次算子提交变成一次：

- **单步 83ms → 8.8ms**（快约 10 倍）；
- **RTF 2.5 → 0.29**（引擎测速：10.5 秒音频合成 3.0 秒），**总吞吐 ≈ 2.7 倍实时**；
- 顺带把 `ras_sampling` 向量化（原版每步对 65k 词表整体排序 + Python 循环挑 25 个，
  6ms/步；改成 `topk`+`cumsum`，分布完全一致）；
- GPU 功耗从 31W 涨到 58～76W —— 显卡终于真的在干活，DVFS 自己就会 boost，
  起播 burst 因此改成自动跳过（`graph_decode` 开启时）。

实现在 `tts_cosy_server.py` 的 `GraphDecoder` / `setup_graph_decode`，不动
`.cosyvoice-src` 源码。开关：`COSY_TTS_GRAPH=0`（退回 eager）、
`COSY_TTS_FAST_SAMPLING=0`（退回原采样）。`/health` 里能看到
`graph_decode` / `fast_sampling` 两项。局限：图只有一份，多请求时解码串行
（但单步 8.8ms，串行也远超实时；flow/hift 仍可并行）。

然后是影响 RTF 的其余几项：

- **显卡频率（最大的一项，常被忽略）**：CosyVoice 是逐 token 出的自回归小模型，
  跑起来 GPU 利用率只有三成多、功耗 40W（上限 165W）。英伟达的自动调频据此认为
  "没在干活"，会把频率压到 450MHz 左右 —— 同一句话 **9.9 秒变 22 秒**，RTF 1.07 → 2.4。
  而系统进入低功耗待机（屏幕熄灭 / Modern Standby）时必然如此，偏偏"躺着听书"
  就是这种场景。两处应对：
  - 引擎在播放期间会按住电源请求（`keep_display_awake`，默认开），不让系统进待机；
    暂停/停止即松开。这一条只在"还没睡下去"时有用，已经睡下去就得靠下面这个。
  - **启动 TTS 时自动锁频**（1.10.4，`gpu_clock_lock` 默认 `"1800"`）：引擎每次
    拉起本机 TTS 都会跑 `nvidia-smi -lgc 1800,<上限>` 把频率锁住 —— 锁了之后
    **待机也是 1800MHz**，机器睡多久、屏幕黑多久都不再掉频，合成全程满速。
    锁频要管理员：普通权限直接试一次，没权限就弹一次 UAC（点一次「是」即可，
    锁频持续到重启，之后启动不再弹）。不想要就设 `"gpu_clock_lock": ""`；
    临时恢复自动调频跑 `nvidia-smi -rgc`。代价是待机功耗从 ~16W 涨到 ~19W。
  - 想彻底稳：跑一次根目录的 `lock-gpu-clock.bat`（右键管理员），把频率锁在
    1800MHz 以上；想省电再跑 `lock-gpu-clock.bat reset`。等价的手动设置是
    NVIDIA 控制面板 → 管理 3D 设置 → 电源管理模式 → **优先最高性能**，
    以及 Windows 设置 → 系统 → 屏幕 → 显示卡 → 默认图形设置 → **高性能**。
  - 测速结果里现在会带上「显卡 1725/3105MHz · 40W/165W」，掉到上限六成以下会
    直接给提示，不用再猜。
- **显存**：被占满（>12GB/16GB）时 WDDM 会把模型换页，频率同样掉到 700MHz、
  功耗只有 30W。开 `--fp16` 后显存从 12.9GB 降到 5.6GB，RTF 从 2.05 回到 1.06。
  设置项：`tts_local_args`（默认 `--fp16 --preload`，换成空字符串即回 fp32）。
- **音频格式**：MP3 转码每句白送 1.0～1.8 秒，1.10.1 起默认走 WAV（见上一节）。
- **并发度**：图解码之后单条就是 1.9～2.1 倍实时，两条并飞 **2.7 倍**（前端默认给
  本机引擎同时发两条；`tts_cosy_server.py` 的信号量也是 2）。再多没用 —— 图只有
  一份，解码本身串行，`COSY_TTS_CONCURRENCY` 调到 4 反而掉回 1.7 倍。
- **长句本身**：见上一节「长句自动切两段并发合成」——这是除频率之外的第二大项，
  43 字起 RTF 明显恶化，切分并发后回到 1.1 档。
- 想彻底稳：跑一次根目录的 `lock-gpu-clock.bat`（右键管理员），把频率锁在
  1800MHz 以上；想省电再跑 `lock-gpu-clock.bat reset`。等价的手动设置是
  NVIDIA 控制面板 → 管理 3D 设置 → 电源管理模式 → **优先最高性能**，
  以及 Windows 设置 → 系统 → 屏幕 → 显示卡 → 默认图形设置 → **高性能**。
  这两项能把 P3/700MHz 顶到 P0/2500MHz，RTF 通常能到 0.5 左右。

### 自带一份 Qwen3-TTS（可选）

`install-tts.bat` → `start-tts.bat`，服务在 `http://127.0.0.1:8890`，
把面板里的地址填成它、点「探测」，音色就会列出来。

- 模型 `Qwen3-TTS-12Hz-1.7B-CustomVoice`：10 种语言，中文音色 5 个
  （`Serena` 温和女声 / `Uncle_Fu` 醇厚男声 / `Vivian` 明亮女声 /
  `Dylan` 京腔男声 / `Eric` 川腔男声），另有 `Ryan` `Aiden` 英文、
  `Ono_Anna` 日文、`Sohee` 韩文。权重在 `models/`，不进仓库。
- 显存约 4.3 GB，加载 7～30 秒，之后常驻。

**实测性能（RTX 4060 Ti 16 GB，很重要）**：RTF 3～7 —— 生成 1 秒音频要算
3～7 秒，而且短句有固定开销（10 字也要 20 秒）。**它不能做逐句实时朗读**，
逐句播会在每句之间卡十几秒。适合的是"质量优先、可以等"的离线合成
（导出整段/整章音频），或者试听音色。

原因是架构：12 Hz 的自回归 talker + 每帧逐码本的 sub-talker，序列长、
串行步数多。这不是配置问题 —— 换 SGLang-Omni 也解决不了，它优化的是
吞吐（并发很多句），不是单句首字节延迟。

所以默认引擎仍然是 `edge`。要"实时 + 本地大模型"，得换非自回归的模型 ——
也就是下面这个。

### 自带一份 CosyVoice2（推荐，音质明显好于 edge）

**一键启动（1.8.0，1.8.1 起连配置都不用填）**：面板 → 语音引擎选「本机大模型 TTS」，
它就会自己把服务拉起来，轮询到真能出声，然后把**实测的地址、模型、音色写回 `config.json`**
并填进面板 —— 8891 是什么端口、模型名该怎么拼，都不需要你知道。
手动点也是同一个按钮：「▶ 一键启动本机 TTS」。

等超过 20 秒还没起来，面板会直接摊开 `tts.log` 的尾巴（缺包、显存不够、解释器选错
一眼就能看见），不用再自己去翻日志文件。

手动启动还是老样子：`start-cosy.bat`，服务在 `http://127.0.0.1:8891`。

- 自定义路径：`tts_local_python`（解释器）、`tts_local_script`（启动脚本），
  留空就自动探测；`tts_local_autostart` 设 false 可关掉自动拉起。

- **架构**：flow matching，非自回归 —— 一次前向出一整段音频，不像 Qwen3-TTS
  那样一个 token 一个 token 地吐，这就是它快一个数量级的原因。
- **音色**：`CosyVoice2-0.5B` **不带预置音色**（`list_available_spks()` 是空的），
  只支持 zero-shot 克隆 —— 每个音色都是一对「参考音频 + 原话」。
  默认音色「默认女声」用仓库自带的 `asset/zero_shot_prompt.wav`；
  想用你自己的声音读书，往 `models/cosyvoice-voices/` 放两个文件：

      models/cosyvoice-voices/我的声音.wav   3～10 秒干净人声，≥16k 采样率，别超 30 秒
      models/cosyvoice-voices/我的声音.txt   wav 里念的那句话，一字不差

  重启服务后音色就多一个「我的声音」，面板里填这个名字即可。
- **显存**：约 3 GB，加载 12～22 秒，之后常驻。

**实测性能（RTX 4060 Ti 16 GB）**

| 文本长度 | 合成 | 音频 | RTF |
| --- | --- | --- | --- |
| 7 字 | 1.9 s | 1.4 s | 1.33 |
| 15 字 | 3.5 s | 3.5 s | 1.00 |
| 29 字 | 5.9 s | 6.6 s | 0.89 |
| 41 字 | 8.3 s | 9.3 s | 0.90 |

也就是**按句朗读时能跟上**（一句话生成得比念完快一点），短句因为固定开销
会慢半拍，靠预取缓冲吃掉。和 Qwen3-TTS 的 3～7 比，这是换了个量级的差别。

**已知的坑：这台机器上速度会掉下去。** 同一天下午用同一份代码、同一个模型重测，
RTF 变成 **2.1～2.6**（41 字要 19 秒），期间 `nvidia-smi` 显示显卡一直停在
**P2 状态**、推理时 GPU 利用率只有 10～40%、功耗 40 W（正常应该能到 P0 和上百瓦）。
纯算力基线（fp32 矩阵乘 20.7 TFLOPS、kernel 发射 0.017 ms）都是正常值，
所以不是模型或代码的问题，是显卡电源状态/驱动那边的事。
遇到"朗读一开始还行、越用越慢"，先看这个：

    nvidia-smi --query-gpu=pstate,clocks.sm,utilization.gpu,power.draw --format=csv

回到 P0 的常见办法：重启机器；或在 NVIDIA 控制面板把「电源管理模式」设成
「最高性能优先」；或关掉一批吃显存的浏览器/Electron 应用。

另外顺手记一笔：**fp16 在这张卡上更慢**（RTF 1.58 vs 1.33），而且音频会短一截
（质量下降），所以默认用 fp32。TF32 只快 7%，默认不开。

#### 这套环境当初是怎么搭起来的（Windows，踩坑记录）

官方没有 Windows 的一键脚本，下面是我实际跑通的顺序，重装时照抄：

1. `conda create -n cosyvoice python=3.10 -y`
2. `conda install -n cosyvoice -c conda-forge pynini==2.1.5`
   —— pip 在 Windows 上装不了 pynini（要 OpenFst 头文件），只能用 conda。
3. `git clone --recursive https://github.com/FunAudioLLM/CosyVoice .cosyvoice-src`
4. 改 `.cosyvoice-src/requirements.txt`：删掉两行 `--extra-index-url`，
   注释掉 `openai-whisper==20231117`；然后
   `pip install --no-cache-dir -r requirements.txt`
   （`--no-cache-dir` 不是洁癖，是沙箱里 pip 清缓存会触发保护直接退出）
5. openai-whisper 单独装：`pip install openai-whisper --no-build-isolation`
6. **CUDA 版 torch**：PyPI / 清华源的 torch 都是 CPU 版（装完 `torch.version.cuda` 是
   `None`）。从 `https://mirrors.aliyun.com/pytorch-wheels/cu124/` 直接下
   `torch-2.5.1+cu124-cp310-cp310-win_amd64.whl` 和同名 torchaudio，
   `pip install --no-deps <两个 whl>`。**文件名必须保持原样**，改名后 pip 报
   `Invalid wheel filename`。`download.pytorch.org` 在这边只有 0.2 MB/s，2.5 GB 要下 3 小时。
7. `pip install "setuptools<81"` —— setuptools 82 起删了 `pkg_resources`，
   hyperpyyaml 加载 `cosyvoice2.yaml` 时要 import 它，不降级就
   `ModuleNotFoundError: No module named 'pkg_resources'`。
8. `pip install flask`（服务本身要）。
9. **权重**分两处下（ModelScope，`iic/CosyVoice2-0.5B`）：
   - `pretrained_models/CosyVoice2-0.5B/` 下的 campplus / flow / hift / llm / onnx 等；
   - **仓库根目录**的 `CosyVoice-BlankEN/`（约 1 GB，Qwen2.5-0.5B 主干），
     下完放到 `pretrained_models/CosyVoice2-0.5B/CosyVoice-BlankEN/`。

   注意：`pretrained_models/CosyVoice2-0.5B/CosyVoice-BlankEN/` 这个路径在仓库里也存在，
   但里面是 6 个 145 字节的空壳（`文件内容为空`），照那个下会报
   `SafetensorError: Error while deserializing header: header too large`。
   判断方法：正常文件是 988 MB，空壳是 145 字节。
10. **wetext 的 fst**：`wetext` 用自己的 `snapshot_download` 拉 `pengzhendong/wetext`，
    在这台机器上稳定 403。直接从
    `https://modelscope.cn/models/pengzhendong/wetext/resolve/master/zh/tn/tagger.fst`
    （zh/en 各 `tagger.fst` + `verbalizer.fst`）下到 `models/wetext/zh|en/tn/`，
    服务启动时会把 `snapshot_download` 指过去。没有它也能跑，只是「10 点」不会读成「十点」。

### 为什么没上 SGLang

SGLang-Omni 确实原生支持 Qwen3-TTS / Higgs Audio v3 / MOSS-TTS / Voxtral，
接口同样是 `/v1/audio/speech`，吞吐比原生 transformers 高得多。但它只支持
Linux（NVIDIA 走 Docker，Apple Silicon 走 `install.sh`）：Windows 上
`pip install sglang-omni` 直接 `ResolutionImpossible`（triton / flashinfer
没有 Windows wheel）。所以这里用官方 `qwen-tts` 原生推理，接口保持一致 ——
哪天把模型挪到有卡的 Linux 机器上跑 `sgl-omni serve`，这边只改地址。

## 边听边问（MiniCPM-o 4.5）

使用 [Comni](https://github.com/tc-mb/llama.cpp-omni#-recommended-companion-demo--minicpm-o-demo-comni) 的 MiniCPM-o 4.5 量化模型启动本机推理 Worker 和网关。ReadAloud 连接网关的音频双工接口。网关需使用 HTTP 并仅监听 `127.0.0.1`，默认端口为 `8040`。从源码启动网关时，可使用 `python gateway.py --http --host 127.0.0.1 --port 8040`，Worker 的启动方式见 Comni 的部署说明。

打开本机 ReadAloud 工作台，展开「边听边问」，点击开启并允许使用麦克风。朗读时直接开口，播放器会暂停，等回答播完后从原处继续。每次最多播放 10 秒回答，等待回答超时也会恢复朗读。会话开启期间可以多次提问，点击「关闭边听边问」会关闭麦克风。浏览器会尝试过滤朗读和回答的回声，实际效果取决于麦克风和房间环境。

ReadAloud 在会话开启时发送当前句和附近文稿。读到其他段落时，可以在问题里直接说出词头或引用原句。麦克风音频和文稿片段在本机浏览器与 Comni 之间传输。

16 GB 显卡建议先选 `Q4_K_M`，并为 Comni 留出显存。如果 Ollama 仍驻留其他模型，先停止闲置模型再开启会话。Comni 默认保存会话录音，可在它的配置中设置 `recording.enabled` 为 `false`。

## 贴个链接就能听

贴链接 → 抓正文 → 开读，默认 **0.2~1 秒**（走规则抓取，不动用模型）。
抓完会在输入框下方摊开一份诊断：标题、字数、段落数、用了哪条提取路线、清掉多少行网页残留、
抓取质量分（0-100），以及模型做了什么。不用猜"到底抓到没有、抓得对不对"。

- **按原文朗读**，不会偷偷缩成摘要（要摘要点「✨ 总结」）。这点很关键 ——
  "智能模式"原本对长文会自动先总结，贴链接时会把一篇 2400 字的文章压成 170 字，
  用户以为在读文章，其实在听摘要。
- **勾「智能整理」**才唤醒本机小模型，直接对已抓到的稿子做深度清理：
  删掉头尾混进来的导航、推广语、"关注我公众号"、相关文章墙。实测 0.8 秒。
- 微信 / 掘金 / 少数派 / 维基 / 博客 / 英文站都能抓；知乎这类要登录的会**明确告诉你原因**，
  而不是丢一句"抓取失败"，并给一个「🧠 让模型硬试一次」的按钮。
- **本机 / 内网地址（`127.0.0.1`、`192.168.*`、局域网机器名）永远直连**，不走系统代理 ——
  否则代理够不到回环地址，只会回一个 502，把自己起的服务挡在门外。

**模型只在该上场时才上场。** 抓得干净（质量分 ≥65）就直接返回，一点算力都不烧；
抓不到时不空喊模型（换身份重抓撞的是同一堵墙，实测白烧 39 秒），直接如实报错。
只有"抓到了但很脏"或用户要求深度清理时，才交给会调工具的小模型。

> 深度清理走的是**单步**调用（直接 `clean_page`），不绕工具回路 ——
> 清理本来就是一个动作，让模型先"决定去抓"再"决定去清"纯属浪费一轮。

## 导入本地的书

点「导入本地文件」选一本书，解析出正文后直接开读，支持 **TXT / EPUB / MOBI / PDF**。
文件只在导入的一瞬间发给你自己的本机引擎（`127.0.0.1:8759`），落在内存里解析，
**不存盘、不上传、不经过任何第三方**。

- **导入后强制按原文朗读。** 书籍动辄十几万字，如果继承下拉框里的「智能」模式，
  点一下朗读会被"长文自动总结"压成几千字——你以为在听书，其实在听梗概。
- **MOBI 自己解。** 支持未加密的 PalmDOC（压缩类型 1 / 2），不引入 GPL 依赖。
  带 DRM 的、以及 HUFF/CDIC 压缩的会明确告诉你原因，而不是吐出几万字乱码。
  PalmDOC 每条记录常带几个尾字节填充，解析时按声明长度截断——
  不截断的话 UTF-8 会在每个 4 KB 边界错位，中文整章变乱码。
- **PDF 靠 PyMuPDF**（`requirements.txt` 已含）。扫描件没有文字层，会提示
  "没有从文件中提取到可朗读的文本"，不会假装读出来了。
- **上限**：文件 80 MB（`MAX_CONTENT_LENGTH` 在解析之前就挡住，超了回 413）；
  EPUB 解压后 200 MB、最多 2000 个条目，防止 zip 炸弹。
- 只想读一段的话，直接往文稿框里粘文字仍然是最快的路径。

## 它比"能出声"多做了什么

**朗读稿是"洗"过的，不是直接把原文字念出来。**

* 结构感知：先认出标题 / 列表 / 引用 / 代码 / 表格，再决定怎么读 ——
  标题会慢一点、多停一会儿，代码和表格直接跳过，列表一条条念。
* 逐句是真逐句（约 60 字/句），所以高亮跟着声音走，还能做句间停顿；
  标题后停 760ms、段末停 660ms、句间停 330ms —— 不是 mp3 一个接一个无缝连读。
* 读音规整（不开 AI 也生效，零延迟）：
  `2026-10-14` → 2026年10月14日、`62%` → 百分之62、`¥1,280` → 1280元、
  `3.5–4.2` → 3.5到4.2、`v1.1.0` → 版本1.1.0、`HTTP/2` → HTTP 2、
  `（上季度55%）` → 逗号承接（念起来有停顿）、URL → "网页链接"。
* 你还能在 `pronounce.json` 里加自己的发音（`K8s` → `Kubernetes`），改完立刻生效。

**它会挑音色，而不是让你在 66 个里猜。**

按内容推荐：中英夹读用多语种音色、技术稿用沉稳播报音、故事用叙事音、粤语用粤语音色。
不确定就先点「🔈 试听」。

**等待时间被消掉了。**

* AI 结果**落盘缓存**：同一段文字第二次点朗读是 0 秒（实测 34.5s → 0.005s）。
* 长文（> `long_doc_chars`）自动**分块提炼再合并**，避免撞上 8k 上下文被静默截断。
* 「智能」模式：短文直读，长文自动先总结 —— 你只需要点一次朗读。
* 生成过程可取消，进度可见，不再是一块什么都不动的遮罩。

**听感可以随时改，不用从头再听。**

* 改语速/音色/音量**从当前这句生效**，不打断、不回到第一句。
* 底部播放条：上一句 / 播放暂停 / 下一句 / 重读本句 / 停止，进度条可点击跳转，显示剩余时长。
* 定时停止（5/15/30/60 分钟或读完当前段）—— 睡前听。
* 夜间模式、`空格`/`←`/`→`/`Esc` 全键盘操作、最近朗读记录、润色后可一键撤销回原文。

## 安装（一次性）

1. 下载本仓库（`Code → Download ZIP`）解压
2. 双击 **`install.bat`** —— 自动建环境、装依赖、注册 `readaloud://` 协议
3. 完事。之后**所有操作都在浏览器里**：在工作台页面点「一键启动本机引擎」即可

依赖只有 Python 3.10+ 和三个包（`edge-tts`、`flask`、`requests`）。
AI 功能额外需要 [Ollama](https://ollama.com)；没有也能正常朗读，只是「总结 / 润色」不可用。

## 在 GitHub Pages 上用

页面部署在 `docs/`，开启 Pages 后地址形如 `https://<用户名>.github.io/readaloud/`。

从云端页面连本机引擎时，浏览器会问一次是否允许「本地网络访问」（Chrome 142+ 的安全机制）——
**选允许即可**，之后不再打扰。顺手点一下「允许」的代价，换来的是文字和模型全程只在你本机。

## 接口速查

| 接口 | 用途 |
| --- | --- |
| `POST /api/prepare` | 一步到位：清洗 →（可选）AI → 规整 → 逐句。返回 `items[{text,kind,pause,rate}]` + 推荐音色 |
| `POST /api/plan` | 只清洗+规整+逐句，不碰 AI |
| `GET\|POST /api/fetch?url=` | 抓网页正文。返回 `title/text/chars` 外加 `quality`（0-100 质量分）、`route`（用了哪条提取路线）、`dropped`（清掉多少行网页残留）、`diag`（试过哪些策略） |
| `POST /api/import` | 上传一个本地文件（`multipart/form-data`，字段名 `file`）解析成正文并自动入库。返回 `title/type/text/chars/book`；格式不支持或读不出来回 400 与中文原因，超过 80 MB 回 413 |
| `GET /api/books` | 书架列表（按最近动过排序），含进度百分比与本数/占用 |
| `GET /api/books/<id>` | 读一本书：`book.text` 是全文，`book.progress` 是上次读到的位置 |
| `POST /api/books/<id>/progress` | 写进度 `{next,total}`（允许倒退），页面关闭时用 sendBeacon 兜底 |
| `DELETE /api/books/<id>` | 从书架删掉一本书（正文一起删） |
| `GET\|POST /api/tts/providers` | 语音引擎：查询/切换 `edge` 与 `local`，POST 带 `probe:true` 会探测本地 TTS 并返回模型与音色表 |
| `POST /api/tts/local/start` | 一键拉起本机大模型 TTS：按脚本挑解释器（cosy→conda env，qwen→`.tts-venv`），状态机立即返回，就绪看下面的 status |
| `GET /api/tts/local/status` | 本地 TTS 状态：`up`/`probe`（引擎名、模型、音色）/`starting`/`python`/`script`，以及 `config`（已自动写回的地址与音色）和 `log`（没起来时的 `tts.log` 尾巴） |
| `GET /api/version` · `POST /api/restart` | 引擎版本与能力清单 / 原地热重启（进程号不变，先确认新代码能编译再关旧监听） |
| `GET /api/update` · `POST /api/update` | 查有没有新版本（`behind` 落后几个提交）/ 升级（`git pull --ff-only` + 重启；工作区脏时拒绝，回 409） |
| `GET\|POST /api/lan` | 手机访问：查询局域网地址与访问码；POST `{host:"0.0.0.0"}` 开启（需重启引擎生效） |
| `POST /api/agent` | 让会调工具的小模型主导取稿。body：`{url, clean, model, retry}`。先走零模型开销的规则抓取（通常 <1 秒）；抓得够干净就直接返回，彻底抓不到就直接报错（`retry:true` 才让模型硬试）；勾 `clean` 时直接深度清理。返回 `trace` 记录模型每一步动作 |
| `GET\|POST /api/login` | 登录态管理。GET 返回各站配置状态与本机可借用的浏览器；POST 按 `action` 分派：`import`（从浏览器整套搬 cookie，可带 `warmup` 预热）/ `paste`（手工粘贴，支持纯 Cookie 头、Network 整行、Copy as cURL 三种粘法）/ `clear` / `open`（开一个带调试端口的登录窗口）/ `probe` / `test`（用当前登录态试抓一个链接） |
| `POST /api/ai` | 总结 / 润色（`stream=true` 可流式，结果自动缓存） |
| `GET /api/tts?text=&voice=&rate=&pitch=&volume=` | 直接返回 MP3 |
| `GET /api/tts/bench?text=&voice=` | 测速度：用带时间戳的文本绕开缓存真合成一句，返回 `rtf`（合成 1 秒音频要几秒）与 `verdict` 分档建议 |
| `POST /api/presynth` · `GET` · `POST /api/presynth/cancel` | 后台预合成全文：启动（`items` + 播放参数，可带 `from` 从第几句续备）/ 查进度 / 停止。缓存键与 `/api/tts` 完全同源，预合成过即秒回 |
| `POST /api/presynth/hold` | 让路协议：`{on:true}` 开播后一句都不再合成，同时按住电源请求不让系统进待机（否则显卡掉到 500MHz）；`{on:false, at:N}` 暂停时松开并把队列挪到第 N 句继续备 |
| `GET /api/recommend` | 按内容推荐音色 |
| `GET\|POST /api/settings` | 记住 AI 偏好（会注入提示词）与朗读选项 |
| `POST /api/broadcast` · `GET /api/events` | 剪贴板/热键 → 已打开的播放页（SSE） |

## 读网页是怎么做的

抓取引擎在 `webfetch.py`。目标不是"把 HTML 转成文本"，而是"还原一份人念得下去的稿子"，
所以要额外解决四件事：

- **编码探测**：很多站点 `Content-Type` 只写 `text/html` 不给 charset，requests 会退回
  ISO-8859-1，中文整段乱码。按「HTTP 头 → meta → 字节猜测」三层定编码。
- **段落重排**：英文站用硬换行排版，一段话被拆成十几行，直接读就是"半句话、停顿、半句话"。
  按句末标点把碎行接回完整段落；标题/引文/列表项则独立成段。
  **顺序不能反**：清噪声要在重排**之前**先做一遍，否则作者卡片、"7 分钟阅读"这类
  又短又没有句读的碎片会被 reflow 粘进正文段落，再也分不开。但重排前只清含中文的行 ——
  英文站的短行是正常的正文碎片。
- **噪声清理**：导航、面包屑、推广语、相关文章墙、二维码提示、作者简介、赞赏按钮文案……
  规则先过一遍，剩下拿不准的交给模型（`/api/agent`）。
- **结构保留**：`<h1>-<h6>` / `<blockquote>` / `<li>` 会转成 `#` / `>` / `-` 标记带下去，
  这样 `text_nlp` 才认得出标题、引文、条目，朗读时才有"标题慢读、条目紧凑、引用留白"的语气分层。
  缩进过的 HTML（`<h1>\n  标题\n</h1>`）会把井号和标题拆成两行，必须粘回去。
  **注意：这条链路中途不能再调 `clean_text`** —— 它会把标记一起洗掉，每篇网页都会退化成
  "全是普通段落"，读着是平的。`selftest_fetch.py` 第 4/6 节专门锁住这两点。
- **代理绕行**：回环 / 内网地址一律不走代理，且在 requests 层面显式关掉 ——
  只传 `proxies=None` 不够，它还会去读环境变量里的 `HTTP_PROXY`，
  把"直连"偷偷变成"走代理"，回环地址就只能拿到一个 502。

模型只在需要时上场：抓得干净（质量分 ≥65）就直接返回，不烧一点算力；
"抓到了但很脏"或用户勾了「智能整理」时才启动模型。**彻底抓不到时不叫模型** ——
auto 模式已经把桌面/手机两种身份都试过，模型再抓撞的是同一堵墙。

给模型挑的是**会调工具但不思考**的模型（`pick_agent_model()` 自动选）。本机的 qwen3 系列
一律带 thinking，做"哪些行是网页垃圾"这种判断时输出只有十来个字符，却要先思考几十秒
（实测 qwen3:4b 清理一次 175 秒，qwen2.5:7b 只要 6 秒，而且判得更准）：

```bash
ollama pull qwen2.5:7b   # 会调工具、不思考，取稿 Agent 用它
```

**提示词里别写否定式约束。** 系统提示里曾有一句「只输出工具调用，不要输出解释性文字」，
结果 qwen2.5:7b 直接吐空回复（连 `tool_calls` 都没有），4 次里 0 次成功；
换成肯定式的「每一轮都调用一个工具，工具调用就是你这一轮的全部回答」后 4/4 成功。
小模型处理"不要做 X"远不如"要做 Y"可靠。

## 知乎 403 怎么解决（登录态）

知乎、小红书这类站**没有登录态就是不给内容**。实测（2026-10-16）：

| 请求方式 | 结果 |
| --- | --- |
| 裸 requests | HTTP 403，返回 650 字节的 zse 挑战页 |
| 带浏览器 cookie（未登录） | HTTP 200 —— 风控过了，但正文是软 404 |
| 带浏览器 cookie（已登录） | 正常全文 |

所以这事跟 UA 无关，跟**有没有登录凭证**（知乎的 `z_c0`）有关。解法在页面右上角的
「🔑 登录态」面板里，两条路：

1. **从浏览器导入**（推荐）：点「🪟 打开登录窗口」→ 在弹出的窗口里登录一次 →
   点「📥 从浏览器导入」。走 CDP 从浏览器实时取 cookie，连 HttpOnly 的 `z_c0`
   都能拿到，一次配好长期有效。抓取时撞上 403 还会自动刷新登录态重试。
2. **手动粘贴**：浏览器 F12 → Network → 刷新 → 点任意请求 → 复制
   `Request Headers` 里的 `Cookie` 整行 → 粘进面板。**必须从 Network 面板复制**，
   Console 里敲 `document.cookie` 拿不到 HttpOnly 的 `z_c0`。

为什么不能直接读浏览器的 cookie 数据库：Chrome 127+ 启用 App-Bound Encryption，
本机实测 Chrome 155 的 `Local State` 里只剩 `app_bound_encrypted_key`，解密要走
COM 提权接口 —— 普通进程做不到，所以只能走 CDP 或手工粘贴。

三个实测踩过的坑，都写进了代码注释：

- **cookie 必须和 UA 配套**。`__zse_ck` 与 UA 绑定，拿浏览器的 cookie 配自己的 UA
  反而被判异常。导入时把浏览器真实 UA 一起存下来（无头标识 `Headless` 会抹掉）。
- **凉 cookie 等于没配**。风控 cookie 寿命极短，把浏览器里"十分钟前"的搬过来照样 403；
  让浏览器先真的访问一次站点首页再取，立刻变 200。所以导入支持 `warmup` 预热，
  抓取失败自愈时也会先预热。
- **不能换着身份猛打**。知乎对频率极敏感：同一篇连打 8 次
  （两轮 × 桌面/手机 × 代理/直连）后整站 403。所以带上登录态后第一轮只打一次。

另外，本机对**未监听**的回环端口不做立即拒绝（connect 挂满 2 秒才失败），
扫 5 个空端口就是 10 秒 —— `/api/login` 一度因此要 10.6 秒才返回，
面板打开像卡死。现在先自己做带超时的 TCP 探活（0.12 秒）再发 HTTP，
并且缓存 8 秒。

## 常见问题

**页面显示「未连接本机引擎」**
先点页面上的「一键启动」。如果没反应，说明协议没注册 —— 双击 `install.bat` 或 `install-protocol.bat`。
实在不行就双击 `start-server.bat` 手动启动，再回页面点「重试」。

**浏览器提示被拒绝访问本地网络**
地址栏左侧图标 → 网站设置 → 把「本地网络访问」改成「允许」→ 刷新页面。

**贴了链接但读出来是摘要 / 内容不对**
抓链接默认按**原文**朗读，不会自动缩成摘要（要摘要点「✨ 总结」）。如果内容不对，
看输入框下方的抓取面板：里面有质量分、用了哪条提取路线、清掉多少行残留。
分数低说明这站点在反爬（知乎、付费墙），把浏览器里看到的正文复制过来一样能读。

**贴链接抓不到**
先看面板里的失败原因。需要登录的页面（知乎、付费内容）抓不到是正常的。
反爬站点会明确告诉你"站点正在做安全检测"或"需要登录"，而不是丢一句"抓取失败"。

**总结/润色很慢**
本机装的 qwen3 系列都带 thinking，思考占了绝大部分时间。想要快就拉个不思考的模型
（`ollama pull qwen2.5:7b`）再选它；想要质量就留着 qwen3。两个模型别同时驻留
（16GB 显存会被挤爆）。

**朗读的发音不对**
改 `pronounce.json`，左边写原文、右边写想读成的样子。改完立刻生效，不用重启。

**edge-tts 报 403**
版本太老。`edge-tts` 需 **7.3.0+**（微软换了鉴权令牌方案），`requirements.txt` 已锁定。

## 端口与配置

默认端口 `8756`，改 `config.json` 里的 `port`；也可用环境变量 `READALOUD_PORT` 覆盖。
换了端口后，改浏览器 localStorage 的 `ra.port`，或改 `config.json` 后重启引擎。

`config.json` 里值得动的几项：`max_len`（单句长度上限，默认 62）、`normalize`（读音规整开关）、
`auto_voice`（按内容推荐音色）、`long_doc_chars`（超过就分块总结）、`prefs.style`（AI 偏好）。

**兼容端口**（`extra_ports`，默认 `[8756]`）：同一个引擎顺便监听几个老书签地址，
免得那个端口上躺着一份几周前的旧副本 —— 现象是"页面是新的、点导入没反应"。
热重启时这些兼容端口会被一起收掉再重绑（1.8.2），不会留下"8759 新版 / 8756 旧版"。
